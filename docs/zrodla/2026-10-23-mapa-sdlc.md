# Mapa procesu SDLC — notatki źródłowe (2026-10-23)

Dwie kolejne wersje mapy z rozmowy, z której powstał [plan jednego flow](../plan-jeden-flow-sdlc.md). Zapisane bez zmian treści, jako źródło dla [dokumentu 13](../13-rola-pdi-w-sdlc.md).

- **Wersja 1** powstała przed przejrzeniem repo tf. Zakładała, że schemat artefaktów, planer i triaż trzeba zbudować w pdi. **Zastąpiona przez wersję 2.**
- **Wersja 2** powstała po przejrzeniu tf: tf jest „mózgiem” procesu, pdi robi się cienkie. Plan jednego flow jest jej rozwinięciem (z ID `CHG`/`TSK`/`DEC` zamiast `Change: PRB-123`).

## Wersja 2 (po przejrzeniu tf)

**Odkrycie:** tf to już „mózg” procesu — fazy 0–9, bramki B1–B6, skille dla każdej fazy, dziennik `docs/project/`, hooki, Talos, triaż (`proc-issue-triage`), pasma kontrolne. Nie trzeba budować od zera schematu artefaktów, planera ani triażu. **pdi robi się dużo cieńsze.** „claude-team-factory” z wersji 1 to w praktyce tf.

Czego tf nie ma: automatu między fazami, UI dla osób nietechnicznych, śladu per zmiana (dziennik per projekt, przebiegi Talosa w ignorowanym `.claude/runs/`), kontroli spójności między źródłami (ci_for_sdlc), statusu wydania (ShipScope).

Zmiany w tf (wersja 2): dziennik per zmiana `docs/project/changes/<ID>/`; stałe ID + dopisek `Change: PRB-123`; Talos z planem i raportem w repo; tryb bez interakcji dla person (stan „czeka na B<n>” sygnalizowany do pdi); `proc-issue-triage` z wejściem z pdi; dokończenie rekonstrukcji; `control_band.py` z wejściem z ShipScope.

Zmiany w ci_for_sdlc (wersja 2): źródło artefaktów tf; źródło wyniku rekonstrukcji (stan as-is bez analizy kodu w ci_for_sdlc); **decyzje zapisywane do `decisions.md` w formacie tf (D-xxx) — „jeden rejestr decyzji dla całego procesu”**; status check na PR, API dla skrzynki pdi; słownik claims per domena; aktualizacja `.claude/`.

Zmiany w ShipScope (wersja 2): źródło zadań poza Jirą (dopisek `Change:`), hierarchia PRB → zmiana → cięcie, release notes z łańcucha, webhook „released”, API statusu, eksport metryk dla `control_band.py`. Wspólne: ujednolicić format dziennika na format tf.

Co nadal dodać (wersja 2): **pdi** — intake + skrzynka bramek + graf śladu (UI dla nietechnicznych; logikę procesu wywołuje z tf, nie powiela); **orkiestrator** (pdi albo GitHub Actions) — „najważniejszy brakujący element”; wykonanie designu w Figmie; AI review w CI; monitoring → `control_band.py`.

Kolejność (wersja 2): 1) dziennik per zmiana + ID + dopisek w tf; 2) rekonstrukcja w tf; 3) ci_for_sdlc czyta artefakty tf; 4) ShipScope czyta dopisek; 5) pdi: intake i skrzynka bramek na `proc-issue-triage`; 6) orkiestrator bez interakcji.
